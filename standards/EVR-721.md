# EVR-721: Mortal Non-Fungible Token Standard

| Field | Value |
|-------|-------|
| **Standard** | EVR-721 |
| **Title** | Mortal Non-Fungible Token Standard |
| **Author** | Satyawan Singh |
| **Status** | Living |
| **Created** | 2026-03-26 |
| **Network** | EvaporChain Testnet |

## Abstract

EVR-721 defines a standard interface for non-fungible tokens with thermodynamic lifecycles on the EvaporChain network. Unlike ERC-721 tokens which persist indefinitely, EVR-721 tokens possess energy that decays exponentially over time according to a configurable half-life. Tokens that are not periodically refreshed will evaporate, transitioning through a grace period before leaving behind a cryptographic ghost record that proves their prior existence. Ghost tokens can be resurrected by depositing new energy.

## Motivation

The permanent storage model of existing NFT standards creates two fundamental problems:

1. **State bloat**: 99% of NFTs minted during 2021-2022 are now economically worthless, yet they permanently occupy blockchain state. On Ethereum, each ERC-721 token consumes ~128 bytes of state storage in perpetuity, with no mechanism for reclamation.

2. **Misalignment with real-world assets**: Physical objects decay, expire, and are consumed. Digital certificates expire. Event tickets become invalid. Insurance policies lapse. Yet the dominant NFT standard (ERC-721) models all assets as eternal, creating a fundamental impedance mismatch between digital tokens and the assets they represent.

EVR-721 solves both problems by giving every token a natural lifespan. Valued assets are refreshed by their owners (paying for continued state occupancy), while abandoned assets return their state to the network through evaporation. Ghost records preserve cryptographic proof of historical existence, enabling resurrection when needed.

## Specification

### Token Lifecycle

Every EVR-721 token progresses through a deterministic lifecycle governed by its energy level:

```
                    refresh()
                   ┌────────┐
                   ▼        │
    mint() ──► [ACTIVE] ────┘
                   │
                   │ energy reaches 0
                   ▼
               [GRACE]  ◄─── grace_period epochs to refresh
                   │
                   │ grace period expires
                   ▼
               [GHOST]  ──── cryptographic proof preserved
                   │
                   │ resurrect()
                   ▼
               [ACTIVE]  ──── token lives again
```

**States:**

| State | Condition | Token Accessible | Transferable | Refreshable |
|-------|-----------|-----------------|-------------|-------------|
| **Active** | `energy > 0` | Yes | Yes | Yes |
| **Grace** | `energy = 0`, within grace period | Read-only | No | Yes |
| **Ghost** | Grace period expired | No (proof only) | No | Yes (resurrects) |

### Energy Decay Formula

Token energy decays exponentially according to:

```
E(t) = E_initial * 2^(-t / half_life)
```

Where:
- `E(t)` is the energy at epoch `t` (epochs elapsed since last refresh)
- `E_initial` is the energy at creation or last refresh
- `half_life` is the number of epochs for energy to halve

**Implementation** (integer arithmetic, no floating point):

```
full_halvings = epochs_elapsed / half_life
remainder = epochs_elapsed % half_life

after_halvings = initial >> full_halvings    // bit-shift for 2^(-n)

// Linear interpolation for fractional decay between halvings
fractional_decay = after_halvings * remainder / (2 * half_life)
result = after_halvings - fractional_decay
```

This provides exact results at half-life boundaries and a close approximation between them, using only integer operations suitable for deterministic on-chain execution.

### Token Schema

```
NftToken {
    id:               u64        // Unique token identifier
    name:             String     // Human-readable name
    collection:       String     // Collection grouping
    owner:            Address    // Current owner (hex-encoded)
    metadata_hash:    Hash       // Blake3 hash of off-chain metadata
    energy:           u64        // Energy at last refresh
    max_energy:       u64        // Maximum energy (at creation/refresh)
    half_life:        u64        // Decay half-life in epochs
    minted_epoch:     u64        // Epoch of creation
    last_refreshed:   u64        // Epoch of last energy deposit
    state:            State      // Active | Grace | Ghost
    grace_epoch:      Option<u64>   // Epoch when grace period began
    evaporated_epoch: Option<u64>   // Epoch when token evaporated
    ghost_proof:      Option<Hash>  // Blake3 nullifier proof
}
```

### Ghost Record

When a token evaporates, a ghost record is created:

```
GhostRecord {
    token_id:          u64       // Original token ID
    owner:             Address   // Owner at time of evaporation
    metadata_hash:     Hash      // Original metadata hash
    evaporated_epoch:  u64       // When evaporation occurred
    ghost_proof:       Hash      // Blake3(token_id : name : epoch)
}
```

Ghost records are stored in a Merkle Mountain Range (MMR) nullifier accumulator, enabling compact inclusion proofs. Any party can verify that a specific token existed and evaporated at a specific epoch without access to the full chain history.

### Required Interface

#### Queries (Read)

| Method | Parameters | Returns | Description |
|--------|-----------|---------|-------------|
| `list_nfts` | — | `Vec<NftResponse>` | All tokens, sorted Active > Grace > Ghost |
| `get_nft` | `token_id: u64` | `NftResponse` | Single token with computed energy |
| `collections` | — | `Vec<Collection>` | Collection list with member counts |
| `energy_of` | `token_id: u64` | `(current, max, half_life)` | Current energy state |
| `state_of` | `token_id: u64` | `State` | Current lifecycle state |
| `ghost_proof` | `token_id: u64` | `Hash` | MMR proof for ghost tokens |

The `NftResponse` includes computed fields evaluated at query time:

```
NftResponse {
    ...NftToken fields...
    current_energy:    u64     // E(now) computed from decay formula
    decay_percentage:  f64     // % of max energy lost
    epochs_remaining:  u64     // Estimated epochs until energy ~0
}
```

#### Mutations (Write)

| Method | Parameters | Auth Required | Description |
|--------|-----------|--------------|-------------|
| `mint` | `name, collection, metadata_hash, energy, half_life` | Sender signature | Create new token |
| `transfer` | `token_id, to` | Owner signature | Transfer to new owner (Active only) |
| `refresh` | `token_id, energy_deposit` | Any signature | Add energy (Active/Grace/Ghost) |

**Mint** creates a new token in Active state:
```
mint(name, collection, metadata_hash, energy, half_life) -> token_id
  Requires: energy > 0, half_life > 0
  Creates:  NftToken { state: Active, minted_epoch: current_epoch }
  Gas cost: 65,000 + creation deposit (proportional to data size)
```

**Transfer** changes ownership:
```
transfer(token_id, to) -> ()
  Requires: caller == owner, state == Active
  Gas cost: 21,000
```

**Refresh** extends token life or resurrects a ghost:
```
refresh(token_id, energy_deposit) -> ()
  If Active/Grace:
    new_energy = current_energy + energy_deposit
    state = Active
    last_refreshed = current_epoch
  If Ghost:
    new_energy = energy_deposit  (fresh start)
    state = Active
    ghost_proof = None           (cleared on resurrection)
  Gas cost: 21,000 + refresh fee (proportional to energy)
```

### Required Events

| Event | Fields | When |
|-------|--------|------|
| `Mint` | `token_id, to, energy, half_life` | Token created |
| `Transfer` | `token_id, from, to` | Ownership changed |
| `Refresh` | `token_id, energy_added, new_total` | Energy deposited |
| `GraceEntered` | `token_id, grace_epoch` | Energy reached zero |
| `Evaporated` | `token_id, ghost_proof` | Grace period expired |
| `Resurrected` | `token_id, new_energy` | Ghost token revived |

### Grace Period

When a token's computed energy reaches zero, it enters the Grace state. The grace period is a network parameter (currently **5 epochs** on testnet) during which:

- The token is read-accessible but not transferable
- Any party can refresh the token to return it to Active state
- If the grace period expires without a refresh, the token evaporates

This mirrors real-world mechanics: an expired insurance policy has a reinstatement period, an overdue library book has a grace period before fines.

### Fee Structure

EVR-721 operations are subject to the EvaporChain fee schedule:

| Operation | Gas | Additional Fee |
|-----------|-----|---------------|
| Mint | 65,000 | Creation deposit (proportional to data size) |
| Transfer | 21,000 | — |
| Refresh | 21,000 | Refresh fee (proportional to energy deposited) |

All fees are burned (deflationary). The creation deposit ensures that minting tokens has an economic cost proportional to the state they occupy.

## Differences From ERC-721

| Feature | ERC-721 (Ethereum) | EVR-721 (EvaporChain) |
|---------|-------------------|----------------------|
| Lifespan | Infinite | Finite (energy-based) |
| State cleanup | Never | Automatic evaporation |
| Storage cost model | One-time gas at mint | Ongoing (refresh to persist) |
| Proof of past ownership | Not possible after burn | Ghost record with MMR proof |
| Resurrection | Impossible | Supported via refresh |
| State cost | Permanent (grows forever) | Proportional to active lifespan |
| Expiry semantics | Manual (smart contract logic) | Native (protocol-level) |
| Burn mechanism | Explicit `burn()` call | Automatic if abandoned |
| Post-death record | None (address 0x0 owner) | Full ghost record with proof |

## Use Cases

EVR-721's mortal token model enables use cases that permanent NFTs cannot natively support:

| Use Case | Half-Life | Behaviour |
|----------|-----------|-----------|
| Event tickets | 1-10 epochs | Auto-evaporate after event |
| Insurance policies | 100-500 epochs | Lapse if premium (refresh) not paid |
| Rental agreements | 30-90 epochs | NFT IS the lease, dies when lease ends |
| Gaming season passes | 50-200 epochs | Evaporate at season end |
| Digital identity/certificates | 500-1000 epochs | Must be periodically renewed |
| Ephemeral messaging receipts | 1-5 epochs | Disappear quickly by design |
| Carbon credits | 100-300 epochs | Auto-retire after use period |
| Art with provenance | 5000+ epochs | Long-lived but not eternal; ghost proves history |

## Security Considerations

1. **Grace period attacks**: A malicious actor cannot force evaporation of another user's token. The grace period provides a window for the owner to respond.

2. **Resurrection front-running**: Anyone can refresh a ghost token, potentially claiming resurrection credit. The original owner field is preserved in the ghost record.

3. **Energy overflow**: Refresh deposits are additive. Implementations must check for integer overflow when computing `current_energy + deposit`.

4. **Deterministic decay**: The integer-only decay formula ensures all nodes compute identical energy values, preventing consensus splits from floating-point divergence.
