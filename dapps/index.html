EvaporChain

data fades unless refreshed

Most chains treat data as immortal — once written, forever stored, forever indexed. EvaporChain inverts that: every contract holds a finite energy that decays automatically; contracts evaporate when the energy runs out unless someone refreshes them. The chain has a structural concept of death — eulogies, tombstones, refresh pools, conservation audits. No other chain has these primitives because no other chain has death to count.

where the math lives

Every decay number on every page resolves through evaporchain-types::energy_at_epoch, a Coq-verified halving formula. The browser dApps inline the same math byte-for-byte so simulations stay consistent with on-chain behaviour.

running these locally
cd dapps/wallet             && npm run serve   # auth front door (port 3000)
cd dapps/decay-vista        && npm run serve   # offline-OK simulator
cd dapps/catalogue-browser  && npm run serve   # port 8088 (serves repo root for .es previews)
cd dapps/four-act-console   && npm run serve   # port 3000 (matches chain CORS allowlist)
cd dapps/block-explorer     && npm run serve   # port 3000 (same as above)
cd dapps/deadman-vista      && npm run serve   # port 8089 (offline-OK simulator)
cd dapps/subscription-vista && npm run serve   # port 8090 (offline-OK simulator)

The two live-data dApps need port 3000 to satisfy the node's CORS allowlist. If another dev server already owns that port (e.g., a Next.js project), either stop the other one or add an extra origin via the EVAPORCHAIN_CORS_ORIGINS env var on the node side and restart.

legacy dApps · pre-existing, need a local build

10 apps

These shipped before the auth + token model and assume their own node URL. They still build and demonstrate doctrine concepts (mortal NFTs, decaying governance, validator analytics).
