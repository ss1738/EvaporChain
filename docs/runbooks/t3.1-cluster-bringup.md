# T3.1 — Cluster Cold Bring-Up Runbook

Operational procedure for standing the 5-node EvaporChain WAN cluster back up
from a **cold / down state** (lane **T3.1** in `MAINNET_READINESS.md`). Last
verified state: **0/5 nodes serving (2026-05-18)** — Minis SSH-flaky, both
Hetzners no API. This runbook takes the cluster from `0/5 → 5/5 healthy` and
hands off to the D-track soak (T0.2).

**Use this when:** the cluster is fully down, or ≥1 validator is down and you
are restoring from scratch. For rolling a *new binary* across an
already-healthy cluster, use `cluster-deploy.md` instead (do **not** duplicate
its stop-the-world classification here). Companion docs: `cluster-deploy.md`,
`validator-onboarding.md`, `disaster-recovery.md`, `monitoring.md`.

---

## TL;DR

1. **Resolve the two operator blockers first (§0):** SSH-auth into both
   Hetzners, and decide whether the soak runs on Minis or a paid VPS pair.
2. **Build on each host** (`cargo build --release -p evaporchain-node`) — never
   on the MacBook; MacBook→Mini scp/rsync silently fails, so `git pull` on the
   host.
3. **Confirm `bls_key.bin` exists on every host before launch** — the launcher
   FATAL-aborts without it, and you must never overwrite it.
4. **Launch via `scripts/launch-tailscale-5node.sh <VID>`** (or the supervised
   `autorestart/install.sh <VID>`); same `--chain-id` (from genesis) on all 5.
5. **Gate on `/api/network/health`** across all 5: `status:"healthy"`,
   `peer_count==4`, `ghost_count==0`, `finalised_height` advancing, identical
   `state_root` + identical `/api/governance/flags`.
6. **Only then** hand off to `scripts/d-track-*.sh`.

## 0. Operator pre-decisions (the actual blockers)

These are not engineering tasks — they gate everything below.

| Decision | Why it blocks | Action |
|---|---|---|
| **Hetzner SSH-auth** | V4/V5 (`root@100.66.208.20`, `root@100.91.235.22`) had no reachable API at last check. Hetzner API `rebuild` can't inject SSH keys — use `enable_rescue` + disk-mount to re-seed `authorized_keys` if locked out. | Confirm `ssh root@<tailscaleIP>` works on both before proceeding. |
| **Minis vs paid VPS for soak** | Minis are chronically unreliable (the reason T3.1 regressed). A representative 72h soak wants stable hosts. | Decide: accept Mini flakiness for a first bring-up, or provision a 2nd paid VPS pair. Cost decision — operator only. |

If either Hetzner is unreachable, **stop and recover it first** — a 5-node
BFT cluster tolerates only `f=1` fault; you cannot launch into a 2-down state.

## 2. Phase A — Host reachability pre-flight

The current failure point. Run from the operator workstation:

```bash
HOSTS="satyawansingh@100.119.53.101 satyawan-mini-1@100.113.253.72 satyawan-mini-2@100.103.216.125 root@100.66.208.20 root@100.91.235.22"
for h in $HOSTS; do
  echo -n "$h: "
  ssh -o IdentitiesOnly=yes -i ~/.ssh/id_ed25519 -o ConnectTimeout=8 "$h" 'echo ok; uptime' 2>&1 | head -1
done
```

**Acceptance:** all 5 return `ok`. Any host that fails → resolve per §0
(Minis: reboot / re-auth Tailscale; Hetzners: rescue-mount to re-seed SSH key)
before continuing.

---

## 3. Phase B — Build the node binary on each host

Build **on the host** (never the MacBook). Per host:

```bash
ssh <host> '
  cd ~/EvaporChain &&
  git fetch origin && git checkout main && git pull --ff-only &&
  cargo build --release -p evaporchain-node &&
  ls -l target/release/evaporchain-node
'
```

Notes:
- Minis hit disk pressure on a full `--workspace` build — build the single
  `-p evaporchain-node` crate, and `rm -rf target/debug/incremental` if low.
- All 5 must be on the **same commit** (`git rev-parse HEAD` should match) —
  a binary skew that changes `state_root` will fork the cluster.

---

## 4. Phase C — Verify keys + genesis present

Per-host validator identity lives in the data dir and must survive across
restarts. **Never overwrite `bls_key.bin` / `network_key.bin`.**

```bash
ssh <host> '
  ls -l ~/.evaporchain-tailscale-5node-data/bls_key.bin \
        ~/.evaporchain-tailscale-5node-data/network_key.bin &&
  ls -l ~/EvaporChain/genesis-tailscale-5node.json
'
```

If `bls_key.bin` is **missing** (the launcher will FATAL-abort), seed it from
that host's saved key bundle (`~/validator-<VID>-keys.json`) — the launcher
prints the exact one-liner; do not regenerate keys, as the genesis pins each
validator's BLS pubkey. If you have no saved bundle, the validator set in
`genesis-tailscale-5node.json` is now wrong for that node and you need a genesis
amendment (see `genesis-amendment-dry-run.md`) — escalate, don't improvise.

> Data-dir wipe (fork recovery only): you may delete chain state in
> `~/.evaporchain-tailscale-5node-data/` but **keep `bls_key.bin` +
> `network_key.bin`**. See `cluster-deploy.md` §5/§7.

## 5. Phase D — Launch

### Preferred: supervised (survives reboot)

```bash
# Macs (V1–V3): installs launchd plist; Linux (V4–V5): installs systemd unit
ssh <host> 'cd ~/EvaporChain && ./scripts/autorestart/install.sh <VID>'
```

`install.sh` auto-detects Darwin→launchd / Linux→systemd and templates the
unit. **launchd PATH gotcha (real incident 2026-05-28):** launchd inherits a
minimal PATH, so the unit MUST export `PATH` including `~/.cargo/bin` — the
shipped plist already does. After install, **smoke-test the unit once** before
trusting `KeepAlive`: a `cargo: command not found` (exit 127) under `KeepAlive`
will respawn-loop and burn the launch. Pre-type `launchctl unload <plist>`
(mac) / `systemctl stop evaporchain-validator` (linux) for a fast unwind.

### Fallback: manual foreground/nohup

```bash
ssh <host> 'cd ~/EvaporChain && ./scripts/launch-tailscale-5node.sh <VID>'
```

The launcher runs `verify-prod-env.sh`, checks binary/genesis/BLS key, kills
any stale PID, builds the full 4-peer bootstrap list, and launches:

```
./target/release/evaporchain-node \
  --tendermint --network --api --mock-prove \
  --genesis-config ./genesis-tailscale-5node.json \
  --validator-id <VID> --validators 5 --node-id node-<VID> \
  --port 9000 --api-port 8081 \
  --data-dir $HOME/.evaporchain-tailscale-5node-data --interval 8000 \
  --bootstrap /ip4/<peerIP>/tcp/9000   # ×4, all other peers
```

**Order:** bring up V4/V5 (stable Hetzners) first, then V1–V3. No DHT in this
build, so the full peer list in the launcher is what forms the mesh; a node
started before its peers will retry-dial and join as they come up.

## 6. Phase E — Health verification gate

Poll all 5 until healthy (API on `:8081`):

```bash
IPS="100.119.53.101 100.113.253.72 100.103.216.125 100.66.208.20 100.91.235.22"
for ip in $IPS; do
  echo "== $ip =="
  curl -s --max-time 10 "http://$ip:8081/api/network/health" \
   | python3 -c 'import sys,json;d=json.load(sys.stdin);print({k:d[k] for k in ("status","block_height","finalised_height","finality_lag_blocks","peer_count","ghost_count","validator_count","jailed_count")})'
done
```

**Acceptance (all 5):**
- `status == "healthy"` (not `syncing` / `stalled` / `isolated`)
- `peer_count == 4`
- `ghost_count == 0` (>0 is the freeze-class early-warning — see §7A)
- `finalised_height` advancing on repeat polls; `finality_lag_blocks` small
- `jailed_count == 0`

Then confirm consensus agreement:

```bash
# state_root must match across all 5 (fork check)
for ip in $IPS; do curl -s "http://$ip:8081/api/status" \
  | python3 -c 'import sys,json;d=json.load(sys.stdin);print(d["state_root"], d["block_height"])'; done

# governance flags must be identical across all 5
for ip in $IPS; do curl -s "http://$ip:8081/api/governance/flags"; echo; done
```

Live view: `python3 scripts/cluster-dashboard.py` (serves
`http://localhost:9090/`, polls all 5). `scripts/check-consensus.sh` /
`check-testnet.sh` exist but target local devnet ports (19001 / 18001-4) — for
this WAN cluster curl `:8081` directly as above.

## 7. Failure modes & recovery

**A. Sybil idle-tick freeze (Lane R.\*).** Symptom: cluster halts at a fixed
height; a validator stuck on a different `state_root`; can't reach 2/3+1.
Diagnose: `/api/network/peers` shows a peer with strongly negative `score`;
`/api/network/scores` shows `ghost_count > 0`; check `/api/network/banned`.
Fix: `POST /api/network/unban` the validator IP; on restart confirm `score:0`
after >5 min uptime and `ghost_count==0`. (Root cause patched in R.1/R.3, but
unban is the operational recovery.)

**B. Chain-id / topic contamination.** Symptom: nodes cross-talk or won't
gossip. Cause: empty/mismatched `--chain-id` falls back to unscoped topics.
Fix: all 5 must launch with the **same non-empty chain-id** (sourced from
`genesis-tailscale-5node.json`); the node refuses to start on an empty one.

**C. Single-bootstrap mesh failure.** A node bootstrapped with only one
neighbour can't discover the rest (no DHT). Always launch via
`launch-tailscale-5node.sh` so the full peer list is wired.

**D. mDNS LAN pollution.** Keep mDNS off (default) on a Tailscale/WAN cluster.

**E. Missing BLS key after wipe.** Restore `bls_key.bin` from
`~/validator-<VID>-keys.json` before restart (see §4). Never regenerate.

## 8. Handoff to D-track soak (T0.2)

Once the gate in §6 passes, T3.1 is **DONE**. Update the lane in
`MAINNET_READINESS.md`, then start the soak suite (these are what T0.2 needs):

```bash
TARGETS="100.119.53.101:8081,..." TPS=1000 DURATION=$((72*3600)) \
  ./scripts/d-track-soak.sh            # D.2/D.3 72h sustained load
./scripts/d-track-adversarial.sh       # D.1 10-vector adversarial API sweep
./scripts/d-track-fault-injection.sh   # D.4 kill 1-of-5, quorum holds + resync
./scripts/d-track-partition.sh         # D.5 partition + heal re-convergence
```

Seed accounts first with `POST /api/faucet` (run nodes with
`--faucet-rate-limit-disabled` for soak) or `scripts/cluster-faucet.py`.

## 9. Teardown / rollback

```bash
# supervised
ssh <host> 'launchctl unload ~/Library/LaunchAgents/com.evaporchain.validator.plist'   # mac
ssh <host> 'systemctl stop evaporchain-validator && systemctl disable evaporchain-validator'  # linux
ssh <host> 'cd ~/EvaporChain && ./scripts/autorestart/install.sh <VID> --uninstall'

# manual
ssh <host> 'kill $(cat ~/evaporchain-5node-v<VID>.pid)'
```

Stopping nodes never deletes keys. A forked cluster has no clean rollback —
recover by wiping data dirs (keep keys) and re-syncing per §4 / `cluster-deploy.md`.
