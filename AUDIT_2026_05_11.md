### AUDIT-2026-05-11-1 + 2 — ShardSample inbound is unrate-limited and unbounded

**Status: CLOSED 2026-05-12.** Inbound-request gate (rate limit + `MAX_SHARD_QUERIES_PER_REQUEST = 256` cap + ban-list violation) landed in `service.rs:1761-1779`. Outbound-response mirror (`validate_shard_sample_response_structure` + ban-list on rejection) landed in `0a62a1d2`. 2 unit tests pin the validator (empty + at-cap-vs-over-cap).

**Site:** `crates/evaporchain-network/src/service.rs:1739..1773`

**Observation:** the inbound `ShardSample` request handler

1. does **not** call `rate_limiter.check_and_increment(&peer)` (compare
   gossipsub at `:1548` and `BlockSync` at `:1614`, which both do), and
2. trusts `request.queries.len()` without an upper bound:
   `let mut samples = Vec::with_capacity(request.queries.len());`
   and then walks every query through `DASampler::generate_proof`
   (Merkle proof construction).

`ShardSampleRequest` (`:101-104`) is just `Vec<SampleQuery>` with no
length cap, and the `request_response::json::Behaviour` is built with
`Config::default().with_request_timeout(Duration::from_secs(10))` —
no `max_request_size`. The libp2p default cap for the JSON codec is
~1 MB; at ~24 bytes per `SampleQuery` that is ≈30 000 queries per
request. Each query runs a Merkle proof.

**Exploit:** a single peer can flood ShardSample with no rate
ceiling, each request forcing ~30k Merkle proof computations, while
its gossipsub and BlockSync rate-limits remain untouched (different
protocol → no shared counter). The other handlers are protected, this
one is not.

**Fix (≈10 lines):**

```rust
const MAX_SHARD_QUERIES_PER_REQUEST: usize = 256;

SwarmEvent::Behaviour(EvaporBehaviourEvent::ShardSample(
    request_response::Event::Message {
        peer,
        message: request_response::Message::Request { request, channel, .. },
    },
)) => {
    if !rate_limiter.check_and_increment(&peer) {
        warn!("Rate-limited peer {peer} — dropping shard-sample request");
        continue;
    }
    if request.queries.len() > MAX_SHARD_QUERIES_PER_REQUEST {
        warn!(
            "Peer {peer} sent {} shard queries, cap is {} — recording violation",
            request.queries.len(), MAX_SHARD_QUERIES_PER_REQUEST
        );
        ban_list.record_violation(peer);
        continue;
    }
    // ... existing handler ...
}
```

Mirror this gate on the outbound response path symmetrically with
`validate_shard_sample_response_structure`, matching the
`validate_sync_response_structure` pattern at `:138-163`.

### AUDIT-2026-05-11-3 — Private-tx gas estimator uses raw arithmetic

**Status: CLOSED.** Estimator at `privacy_exec.rs:906-915` already uses `saturating_add` + `saturating_mul` (matches the parallel.rs pattern the audit cites). Re-verified 2026-05-12.

**Site:** `crates/evaporchain-execution/src/privacy_exec.rs:877-882`

```rust
pub fn estimate_private_transfer_gas(tx: &PrivateTransferTx) -> u64 {
    GAS_PRIVATE_TRANSFER_BASE
        + GAS_PRIVATE_TRANSFER_PER_INPUT * tx.input_nullifiers.len() as u64
        + GAS_PRIVATE_TRANSFER_PER_OUTPUT * tx.output_commitments.len() as u64
}
```

Plain `*` and `+` on `u64`. With `GAS_PRIVATE_TRANSFER_PER_INPUT =
20_000`, wrapping requires `input_nullifiers.len() ≈ 9·10¹⁴` — far
beyond what serde can practically deserialize, so this is not
exploitable in isolation. It is, however, **inconsistent** with the
neighbouring estimators in `parallel.rs:1018-1021`, which already use
the saturating form:

```rust
crate::GAS_USER_OP.saturating_add(tx.call_data.len() as u64 * 16)
```

A wrap here would result in the fee controller charging a small
amount for an enormous transaction. Saturating to `u64::MAX` is the
correct conservative behaviour for any fee path.

**Fix:**

```rust
pub fn estimate_private_transfer_gas(tx: &PrivateTransferTx) -> u64 {
    GAS_PRIVATE_TRANSFER_BASE
        .saturating_add(
            GAS_PRIVATE_TRANSFER_PER_INPUT
                .saturating_mul(tx.input_nullifiers.len() as u64),
        )
        .saturating_add(
            GAS_PRIVATE_TRANSFER_PER_OUTPUT
                .saturating_mul(tx.output_commitments.len() as u64),
        )
}
```

### Closed on inspection (re-checked, no action needed)

These were on the audit candidate list; reading the code shows they
are already defended. Recording so the next auditor does not redo the
work.

- **`crates/evaporchain-crypto/src/signatures.rs:98` — `MlDsaKeypair::from_bytes` unsafe pointer writes.**
  Already mitigates layout assumptions with (1) compile-time
  `size_of::<Keypair>() == PK+SK`, (2) runtime
  `kp.public.as_slice() == pk_bytes && kp.expose_secret() == sk_bytes`
  comparisons after the writes, and (3) a sign-verify canary
  roundtrip. A silent field-order swap by the upstream crate would
  fail check (2). Closed.
- **`crates/evaporchain-network/src/service.rs:1607-1662` — BlockSync inbound.**
  Rate-limited (`:1614`), capped to `MAX_SYNC_BATCH = 100` blocks on
  both serving (`:1623`) and receiving (`:141`,
  `validate_sync_response_structure`). Closed.
- **`crates/evaporchain-consensus/src/api.rs:11757` and `crates/evaporchain-node/src/api.rs:11887` — `_ => unreachable!()`.**
  Both match on `&tx` where `tx` was constructed as
  `Transaction::UpgradeContract(...)` literally seven lines above. The
  unreachable arm is genuinely unreachable. Closed.
- **`crates/evaporchain-execution/src/rewards.rs:400` — `(pool as u128 * stake as u128 / total_stake as u128) as u64`.**
  `u64 × u64` cannot overflow `u128`. The final `as u64` truncation is
  bounded by the invariant `stake ≤ total_stake` (since
  `total_stake = Σ stake_i`), so the quotient is ≤ `pool` which fits
  in `u64`. Closed.
- **WebSocket subscriber cap.** `DEFAULT_MAX_WS_SUBSCRIBERS = 4096`
  enforced at `crates/evaporchain-node/src/ws.rs:183`. Closed
  (matches Audit-N M11).
